## 1. 复现实验的整体方法论

一次论文复现的标准流程（本次完整走了一遍）：

```
① 锁定代码版本（commit hash）与论文版本（arXiv v1/v2）
② 静态分析：读代码结构、硬编码路径、随机种子、数据口径 → 写预执行报告
③ 环境搭建：按架构选 torch 版本 → 装依赖 → 冒烟测试（import + 前向）
④ 数据准备：下载 → MD5 校验 → 核对划分/归一化口径
⑤ 小规模验证：forward-only 测试、3-epoch 试跑、确定性验证
⑥ 正式实验矩阵：任务编排、日志、断点续跑、发散检测
⑦ 结果聚合：与论文逐项对比、相对误差、分级判定
⑧ 消融与归因：异常结果追根因（本次最花时间的部分）
```

**核心心态**：
- 复现的目标不是"跑出数字"，而是"数字可信且可解释"。可信靠确定性验证与口径核对；可解释靠消融与代码考古。
- **先小后大**：任何配置先在 3 epoch 冒烟，再进矩阵。本次矩阵启动前发现了 3 个 bug（AMP NaN、argparse 传值、检测器误杀），全靠冒烟兜底。
- **成本驱动决策**：设计矩阵时先估算每个 run 的时长（steps/epoch × step-time × epochs × 早停概率），再决定数据集/horizon 取舍（本次因此选了 Exchange 而非 Electricity）。

## 2. 环境与依赖管理（坑最密集的区域）

### 2.1 GPU 架构决定 torch 版本

**知识点**：CUDA 二进制不向前兼容架构。每代 GPU 有对应的 `sm_xx` 计算能力，torch 的预编译 wheel 只包含特定范围的 kernel。

| 显卡 | 计算能力 | 可用 torch |
|---|---|---|
| RTX 3050 Laptop | sm_86 | 2.2.2+cu118 |
| RTX 5090 (Blackwell) | **sm_120** | **≥2.7 + cu128** |

**坑**：换机器迁移实验时，环境不能原样拷贝。本地 3050 的 torch 2.2.2 在 5090 上根本没有 sm_120 kernel。迁移手册必须显式列出"哪些包因硬件变化要换版本"。

**排查工具**：`nvidia-smi` 看驱动（5090 需 ≥570.86）；`torch.cuda.get_device_capability()` 看计算能力；装错版本的典型报错是 `CUDA driver version is insufficient` 或 `no kernel image is available`。

### 2.2 依赖版本冲突：pip 解析器的回溯行为

本次耗时最久的一个坑，值得完整理解：

**现象**：装 requirements 时 pip 反复去 PyPI 下载新版 torch（2.14/2.13/2.12……），每次下载几百 MB 后失败。

**根因**（两层）：
1. **真正的冲突**：`requirements.txt` 钉死 `sympy==1.11.1`，而 torch 2.7 要求 `sympy>=1.13.3`。pip 无法同时满足 → 开始回溯，尝试"换一个 torch 版本"来兼容 sympy 1.11.1 → 于是一个个下载 PyPI 上的 torch。
2. **误导性的报错**：回溯过程中撞上镜像 hash 校验失败（清华镜像的大文件 CDN 损坏 + 之前中断下载留下的坏缓存），报错信息全是 hash mismatch，完全看不出真正原因是 sympy。

**教训**：
- 看到 pip "looking at multiple versions of X" 时，X 往往不是冲突源而是被回溯的受害者。用 `--dry-run` 让 pip 把解析过程走完，真正的冲突会以 "The conflict is caused by: A depends on B, user requested C" 的形式暴露。
- **锁定关键包 + 约束文件**是标准解法：`-c <(printf 'torch==2.7.1+cu128')` 把回溯空间钉死，冲突立刻现行。
- 镜像 hash 失败 ≠ 镜像被投毒：先 `pip cache purge` 清坏缓存再判断。

### 2.3 生态包的"未固定 torch 依赖"

**知识点**：很多包在 setup.py 里写裸 `install_requires=['torch']`（不写版本），pip 解析时可能决定"换掉已装 torch"来满足别的约束。

**本项目实例**：`reformer-pytorch`、`pytorch-wavelets`、`timm` 及其 lucidrains 系依赖（local-attention、product-key-memory、axial-positional-embedding、hyper-connections、colt5-attention）全部声明裸 torch。

**解法**：对这类包用 `--no-deps` 安装，手工补它们的非 torch 依赖。宁可多装几个小包，也不要让 pip 碰 torch。

**排查技巧**：`pip install --dry-run` 看会动哪些包；`importlib.metadata.requires('包名')` 查某个包声明了哪些依赖。

### 2.4 老包构建的隐藏成本

`pytorch-wavelets==1.3.0`（2020 年的包）：
- 只有 sdist，没有 wheel → pip 要现场构建；
- 它的 setup.py 里 `from torch.utils.cpp_extension import ...` → **构建隔离环境里也要装 torch**，pip 于是又去下载一个全新 torch（几 GB）只为构建元数据；
- 解法：`--no-deps --no-build-isolation`，让构建直接复用当前环境的 torch。

**知识点**：`pkg_resources` 是 setuptools 提供的老模块，setuptools≥81 移除后老包 import 就炸。报 `ModuleNotFoundError: pkg_resources` 时降级 `setuptools<81`。

### 2.5 梯度断链排查（深度学习工程的基本功）

**现象**：E1 实验中图像生成器的参数"训练后与随机初始化逐位相同"——它从来没被训练过。

**排查方法**（通用的断链定位流程）：
1. 对怀疑的模块做 backward 检查：`{n}/{N} params got grad` —— 0/N 即断链；
2. 在数据流各阶段 hook 检查 `requires_grad`，二分定位断点；
3. 找到断点后问"这里有什么不可微操作"。

**本项目发现的三种断链**（按层次记）：
| 断链操作 | 位置 | 为什么不可微 |
|---|---|---|
| `.to(torch.uint8)` | 图像归一化 | 量化强转，autograd 直接断 |
| PIL 往返（processor 内部 resize） | CLIPProcessor | tensor→PIL→tensor 走了 numpy/CPU 拷贝 |
| `tensor.detach()` | 可视化工具误用 | 显式脱离计算图 |

**教训**：一个"看起来能训练"的模块可能从设计上就收不到梯度。验证"参数真的动了"（checkpoint vs 随机初始化的逐位对比）应该成为复现的标准检查项——本次正是这个检查把 VLM 无贡献的头号根因挖出来的。

### 2.6 HF 模型缓存

**知识点**：huggingface 缓存 = `blobs/`（内容寻址的文件实体）+ `snapshots/`（软链接）。下载中断会留下 `.incomplete` 文件或截断的 blob，而 `local_files_only=True` 加载时会静默失败并回退到在线下载（慢、且在国内网络会卡死）。

**本项目实例**：CLIP 的 pytorch_model.bin 截断在 605,123,003 字节（差几 KB），torch.load 报 "Unable to load weights"。修复 = 删坏 blob 重下 + `HF_HUB_OFFLINE=1` 验证离线加载。

**排查技巧**：
- `du -sh` 对比 blob 实际大小与预期（HF API 可查文件列表）；
- 网络受限时 `export HF_ENDPOINT=https://hf-mirror.com`；
- 大文件下载加 `HF_HUB_DISABLE_XET=1` 走普通 HTTP（xet 协议在镜像上不稳定）。

## 3. GPU 显存：读 OOM 报错 + 手算张量

**知识点**：OOM 报错里的 "Tried to allocate X GiB" 反推张量形状，是显存分析的基本功。

**本项目实例**：Time-LLM 在 ECL（321 通道）上 OOM，报错 "Tried to allocate 19.29 GiB"。反推：19.29GiB / 4B = 4.8G 个元素 = 10272（B×N=32×321）× 8（heads）× 64（patches）× 1000（text tokens）→ 正是 ReprogrammingLayer 的 `scores` 张量。

**通用经验**：
- 注意力类模块的显存杀手是 `[B, heads, L, S]` 的分数矩阵（L、S 任一个上千就危险）；
- 通道数大的数据集 + 把 B×N 展平成序列的模型（Time-LLM 的 reprog、GPT2 路径）= 显存灾难组合。321 通道 × batch 32 = 10272 个序列，seq 96 都不够救；
- 手算一遍：`元素数 × 4 字节（fp32）`，再乘 2（前向+反向），留 20% 余量；
- 放弃也是一种结果：记录"为什么不行"（B×N 展平不经济），比硬凑 batch=1 跑 30 小时有价值。

**排查工具**：`torch.cuda.memory_allocated()`、`nvidia-smi`（注意它的显示含缓存碎片）、`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`（缓解碎片化）。

## 4. 数据与评估口径

### 4.1 数据集镜像与格式转换

- 墙内拿 GitHub 数据：`api.github.com` 通常通、`github.com`（git 克隆/raw）通常不通 → 用 **jsDelivr**（`cdn.jsdelivr.net/gh/{user}/{repo}@{ref}/{path}`）下载仓库文件；
- laiguokun 的多变量数据集存的是 `.txt.gz`（无表头、无日期列），而 DataLoader 要求 csv + `date` 列 → 要自己重建日期列。**日期列影响 baseline 的 timeF 特征**（month/day/weekday），对 TimeVLM 无影响（它不用时间戳特征）。重构时选 business days 还是 calendar days 要记录清楚；
- 这个仓库的 `Dataset_Custom` 有隐性约定：csv 必须含 `date` 列和一个 `--target`（默认 'OT'）列，且 features='M' 时 **target 列也参与特征** → 构建 ECL/Exchange 的 csv 时把最后一列改名 'OT'，正好凑出 enc_in=321/8。

### 4.2 归一化口径决定数字可比性

- 评估在 StandardScaler 归一化空间（脚本不传 `--inverse`），论文同口径，所以 MSE 0.36 这种数字才能直接对比；
- 划分是 12/4/4 月固定边界（8545/2881/2881 是论文口径，仓库代码是 8640/2880/2880）——数据集划分不同，数字就会系统性偏移，对比前必须核对。

### 4.3 few-shot / zero-shot 的机制

- few-shot：`task_name=few_shot_forecast` + `--percent 0.1`，采样发生在 `data_provider`（只抽训练集），exp 逻辑与 full 相同；
- zero-shot：`exp_zero_shot_forecasting` 在测试阶段深拷贝 args 换成目标数据集（`target_data/target_root_path/target_data_path`），**训练全程只用源域数据**；
- **坑**：很多模型（PatchTST/iTransformer/TimeLLM）的 forward 按 `task_name` 分支，只认 `long_term_forecast/short_term_forecast`——传 few/zero 的 task_name 会直接不建 head/返回 None。通用修法：模型 `__init__` 里把 few/zero 归一化成 long-term（数据采样由 data_provider 管，模型不需要知道）。

## 5. 训练稳定性与实验管理

### 5.1 确定性验证（复现的"可信度基石"）

**知识点**：固定 seed（random/numpy/torch）+ 无随机增强 + 单卡 = 通常可逐位复现。DataLoader 的 batch 顺序由主进程的 sampler 决定（worker 不改变顺序），所以多 worker 不破坏确定性。

**本项目实例**：full h720 重跑，12 个 epoch 的 loss 和最终 mse（0.45236241817474365）逐位一致。这个验证后来成为排除"消融差异是噪声"的关键证据。

**应用**：怀疑"结果差异是运气"时，重跑一次看是否逐位一致——是的话，任何差异都来自代码/数据/配置的真实变化。

### 5.2 发散检测与误报

- 首 epoch Vali Loss 远超正常区间（本项目 ETTh1 归一化空间 >2.0）→ 配置/数据有问题的信号，早杀省时间；
- **误报来源**（本次全踩了一遍）：
  1. 早停消息 `Validation loss decreased (inf --> 0.19)` 里的 "inf" 是初始最优值的合法打印 → 正则要锚定在 "Vali Loss:" 字段上；
  2. 大小写不敏感的正则 `inf` 会匹配日志里的 "Info" → 用 `\b(nan|inf)\b` 单词边界；
  3. few-shot/zero-shot 的首 epoch val 天然更高（数据少/域偏移）→ 阈值要分设定设（本次 3.0 误杀 4 个任务，8.0 合适）。

### 5.3 AMP 不是万能的

Time-LLM + `--use_amp`（fp16）在 epoch 2 稳定产生 NaN（GPT2 激活 + 重编程层在 fp16 溢出），去掉后正常。**教训**：新模型进矩阵前必须冒烟；基线模型的官方脚本用了什么精度配置，照抄（TSL 的 Time-LLM 脚本本来就不开 AMP）。

### 5.4 任务编排的工程细节

- **任务命名必须唯一**：本次第一版驱动器的任务名不含模型名，4 个模型的任务互相覆盖 manifest 和日志——排了半天才发现"任务完成记录串台"；
- argparse 的两种布尔参数：`action='store_true'`（**不能带值**，`--use_amp True` 会报 unrecognized arguments）vs `type=str2bool`（必须带值）。看 run.py 定义才能正确拼命令；
- 断点续跑 = 以结果文件/manifest 为准跳过已完成任务；失败隔离 = 单任务 try/except 继续下一个 + 失败清单最后统一处理；
- 结果文件被多次追加后格式会漂移（本项目的 result 文件曾出现 "calculated" 粘连），聚合前先规范化重建。

## 6. 代码考古：质疑官方代码（本次最有价值的部分）

### 6.1 "官方代码 = 正确代码"是误区

**验证方法**：GitHub API 查官方仓库最新提交的 tree SHA，与本地 `git rev-parse HEAD^{tree}` 对比——**逐字节一致**才叫"跑的就是官方代码"。本项目确认：官方 CityMind-Lab 仓库 HEAD（796e6ec）就是我们的训练版本。

**git 考古工具**：`git log --all`、`git show <旧commit>:<文件>`（读历史版本）、`git diff A B -- file`（看演进）。本项目靠 `git show b488910:...` 确认三个"VLM 失效点"在论文时期（2025-05-26）就存在。

### 6.2 死代码识别

读代码时主动问"这个模块被调用了吗"：
- `multimodal_fusion_gate`：在普通 class（非 nn.Module）里创建 nn.Sequential → 从不注册、从不训练、从不调用；
- `self.alpha`：定义成 nn.Parameter 但全库无引用 → checkpoint 里永远是初始值 0.5；
- `w_out_visual/w_out_text`：开关存在但 forward 没接 → 需要补丁才能用的"死开关"。

**排查方法**：`grep -rn "模块名" --include="*.py"` 看引用点；checkpoint 里参数 == 初始值 = 从未被训练。

### 6.3 论文数字的批判性解读

- 论文 Table 6 自己的消融就显示：w/o 时序记忆 +35.6%、w/o 文本仅 +2.1%、h720 上 w/o 视觉反而更好——**论文的数据与其叙事存在张力**，作者在 issue #9 里也承认截断是 "intentional" 且测过完整上下文"无提升"；
- "复现成功（数字一致）"与"论文主张成立（VLM 有效）"是两件事。数字一致只说明你忠实地跑出了作者的代码行为；
- 查 GitHub issues 是考古的重要一环：`api.github.com/repos/{org}/{repo}/issues/{n}` 不用鉴权。

## 7. 消融实验的正确姿势

### 7.1 两种消融的区别（关键概念）

| | 重训练消融 | 同权重干预 |
|---|---|---|
| 做法 | 改配置重新训练（w/o-VLM 独立训） | 加载已训模型，干预输入/中间量后前向 |
| 优点 | 符合"这个组件不存在时"的真实设定 | 隔离了训练随机性的影响 |
| 缺点 | 差异可能来自重训练的轨迹差异 | 只测推理侧，测不到训练侧贡献 |

**本项目实例**：w/o-VLM 重训练比 full 好 2.8%，看似"去掉 VLM 有帮助"。同权重干预显示：把 full 模型的 VLM 嵌入置零，输出 5 位小数不变 → VLM 在全模型里本来就没贡献；2.8% 的差异来自 wovlm 独立训练出了更好的 memory 分支（0.489 vs 0.501）。**两个实验结合才能正确归因。**

### 7.2 checkpoint 探查（直接读模型内部状态）

加载训练好的 checkpoint，用 forward hook 抓 gate 输出：w_multimodal = 0.00077 —— 模型自己学会了关掉 VLM 分支。再做"强制 w_v=1"的干预：MSE 恶化 30-44% → gate 关闭 VLM 是**学出来的正确决策**（分支无信息），不是 gate 有 bug。

**方法论**：一个组件无效时，要区分"被下游压制"（gate 问题）和"本身无信息"（上游表征问题）。用 hook 读中间量、做单变量干预，逐个排除。

## 9. 建议的动手练习（把这次经历变成你自己的）

按难度排序，每个都能在 30 分钟内完成：

1. **复现 E1 的梯度追踪**：在 3050/5090 上对 `learnable_image_module` 做一次 `{n}/{N} params got grad` 检查，然后在 `_normalize_images` 里加回 `.to(torch.uint8)`，观察梯度消失——亲手感受断链。
2. **读 gate 权重**：加载一个 TimeVLM checkpoint，用 hook 打印 gate 的 softmax 输出分布，回答"这个模型在多大程度上使用 VLM 分支"。
3. **做一次同权重干预**：对 full h720 checkpoint，把 vision_embeddings 置零后跑 test，对比 MSE 变化——理解"消融"与"重训练"的区别。
4. **git 考古**：`git show b488910:src/TimeVLM/model.py | grep -n "uint8"` 自己确认论文时期代码的状态；再用 `git log --all --oneline` 梳理官方仓库的演进史。
5. **手算一次显存**：选任意模型，写出注意力矩阵的形状 × 4 字节，估算 batch 翻倍后的显存，再用实际运行验证。
6. **设计一个 mini 矩阵**：选 1 个数据集 × 2 模型 × 2 horizons × 1 设定（4 个任务），自己写一个带断点续跑的驱动脚本（可以比 run_matrix.py 简单得多），跑通后和本次的工程经验对照。

## 10. 一句话总结

复现实验的功夫在"数字之外"：确定性验证建立可信度，口径核对保证可比性，梯度/显存/缓存排查是工程基本功，**git 考古和同权重消融是质疑与归因的利器**——最后这一步，才是从"跑通代码"走向"理解论文"的分水岭。
